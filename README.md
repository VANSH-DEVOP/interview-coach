# InterviewPilot AI

AI-powered interview preparation platform. Users register, upload resumes, run adaptive AI mock interviews, receive evaluation reports, and track progress over time.

Full authentication, resource APIs, a normalised schema, a responsive UI, and a
complete AI pipeline: Gemini question generation and evaluation, hybrid
retrieval over the candidate's own resume, and a durable evaluation queue.

**Every AI path degrades to a deterministic local implementation.** With no
`GEMINI_API_KEY`, or when the provider fails, interviews are still completable
and reports are still produced — they are simply generic. That property is
load-bearing and is preserved deliberately; the degradations are counted and
reported at `/health` rather than hidden.

---

## 1. Project Overview

| Capability | Status |
|---|---|
| Registration / login (JWT, rotating refresh tokens) | ✅ |
| Password reset, email verification, account deletion | ✅ |
| Resume upload, parsing (PDF/DOCX), chunking | ✅ |
| AI question generation, tailored to the resume | ✅ Gemini, with a deterministic fallback |
| Adaptive follow-up questions | ✅ chained by `parent_question_id` |
| RAG over the resume (dense + keyword, rank fusion) | ✅ ChromaDB + Postgres FTS |
| AI evaluation reports | ✅ queued to a worker; the client polls |
| History & progress tracking | ✅ |
| Observability: fallbacks, retrieval, token spend, tracing | ✅ `/health`, LangSmith, Sentry |

Two constraints shape most of the design decisions in this repository, and are
worth knowing before reading the code:

- **The Gemini free tier allows 20 requests per day for the whole account.** It
  is why embeddings are cached, why question generation is one provider call
  and not four, why query rewriting is deterministic, and why generated
  question sets are deliberately *not* cached.
- **A resume is personal data.** Direct identifiers are stripped at the two
  network boundaries before anything reaches a third party — see §7.

## 2. Architecture

```
┌─────────────────────────────────────────────────────┐
│  PRESENTATION · Next.js App Router, TS, Tailwind,    │
│  shadcn/ui · dark enterprise theme · responsive      │
└───────────────────────┬─────────────────────────────┘
                        │ REST /api/v1 · JWT Bearer
┌───────────────────────▼─────────────────────────────┐
│  APPLICATION · FastAPI                               │
│  api (routers) → services (logic) → repositories    │
│  core: settings · security · logging · exceptions   │
│       rate limits · error reporting                 │
│  middleware: error envelope · request logging       │
│              security headers                        │
│  ai/: generation · evaluation · RAG · masking       │
│  seams: StorageService · QuestionGenerator ·        │
│         Evaluator — each with a local fallback      │
└─────┬──────────────┬─────────────────┬──────────────┘
      │ SQLAlchemy   │ Gemini          │ arq / Redis
      │ Alembic      │ (redacted)      │ (evaluation jobs)
┌─────▼───────────┐ ┌▼──────────────┐ ┌▼───────────────┐
│ DATA · Postgres │ │ VECTORS ·     │ │ WORKER · arq   │
│ rows + FTS index│ │ ChromaDB      │ │ app/worker.py  │
│                 │◄┼───────────────┼─┤ + cron sweeps  │
└─────────────────┘ └───────────────┘ └────────────────┘
```

**Retrieval is hybrid.** The dense half is ChromaDB; the keyword half is a
Postgres full-text index on the chunk table, generated by the database itself.
Their rankings are combined with Reciprocal Rank Fusion rather than a weighted
score, because cosine distance and `ts_rank` have different ranges and neither
is calibrated — any weighted sum would be inventing an exchange rate. Either
half failing degrades to the other.

The worker is a **second process running the same image**. Ending an interview
returns immediately with a PENDING report; the evaluation itself is a provider
round-trip, so it is queued and the client polls. Without `REDIS_URL` the API
falls back to in-process background tasks — same result, but a restart loses
the work. See `app/services/job_queue.py`.

**Layer rules**

- Routers never touch the database; they call services.
- Services contain business logic and depend on abstractions (repositories, `StorageService`, `QuestionGenerator`, `Evaluator`).
- Repositories are the only layer that builds SQL, and user-scoped reads go through `get_owned(id, user_id)` rather than `get(id)`.
- Domain errors are raised as typed exceptions and translated to a consistent envelope: `{"error": {"code", "message", "details"}}`.
- Every environment variable enters through `app/core/config.py`. No other module reads `os.environ` — with one documented exception, the LangSmith SDK, which offers no other way in.

## 4. Setup Instructions

### Docker (recommended)

```bash
cp .env.example .env       # then set JWT_SECRET_KEY: openssl rand -hex 32
docker compose up --build
```

- Frontend: http://localhost:3000
- API docs (Swagger): http://localhost:8000/docs
- Health: http://localhost:8000/api/v1/health

Migrations run automatically on backend start.

### Local development (without Docker)

Backend:

```bash
cd backend
python3.12 -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
# Postgres must be running. With the compose stack up, it is on the published
# port (POSTGRES_PORT, 5434 by default) -- not 5432.
alembic upgrade head
uvicorn app.main:app --reload
```

Configuration is read from `<repo>/.env` and then `<repo>/backend/.env`, both
resolved from the source tree rather than from the working directory, so every
entry point sees the same values whichever directory you start it from. **Put
settings in the root `.env`** — it is the file docker-compose reads too.

Set `CHROMA_PATH` to a writable local path when running outside Docker. The
default lives under `/var/lib` and is usually not writable, in which case RAG
disables itself and says so at `/health` — the only other symptom is that the
questions feel generic.

Evaluations run in-process unless `REDIS_URL` is set. To run them the way
production does, start Redis and add a second terminal:

```bash
cd backend
arq app.worker.WorkerSettings     # needs REDIS_URL, same as the API
```

Frontend:

```bash
cd frontend
npm install
NEXT_PUBLIC_API_URL=http://localhost:8000/api/v1 npm run dev
```

Tests:

```bash
cd backend && pytest              # 684 tests
pytest --cov=app                  # with the coverage gate CI applies
```

```bash
cd frontend && npm test           # 53 tests
npm run test:coverage             # with thresholds
```

Tests that need Postgres or Redis **skip** when the service is not reachable, so
`pytest` stays useful with nothing running. CI sets `REQUIRE_TEST_DATABASE=1`
and `REQUIRE_TEST_REDIS=1` to turn those skips into failures — a broken service
container must not produce a green build.

## 5. Development Workflow

1. Branch from `main`.
2. Schema change? Edit models, then `alembic revision --autogenerate -m "describe change"` and review the generated migration.
3. New resource = model → schema → repository → service → router → register in `api/v1/router.py`.
4. Keep business logic in services; keep SQL in repositories.
5. Run `pytest`, `ruff check`, `mypy app`, and `npm run typecheck` before pushing.
6. Open a PR. CI gates merges: dependency audit, ruff, mypy, migration drift and
   reversibility, tests against a real Postgres and Redis with coverage
   thresholds, then the frontend typecheck, tests and build.

CI turns the "service unreachable, skip" paths into hard failures
(`REQUIRE_TEST_DATABASE=1`, `REQUIRE_TEST_REDIS=1`). A broken service container
must not produce a green build.

## 6. The AI pipeline

All of it ships. `backend/AI_INTEGRATION.md` and `backend/RAG_IMPLEMENTATION.md`
go deeper; `CLAUDE.md` records why each decision was made.

| Piece | Where | Notes |
|---|---|---|
| **Question generation** | `ai/gemini.py`, `ai/pipeline.py` | A chain: extract → generate → critique → refine. Only `generate` always costs a provider call — a call per step would take the deployment from ~6 interviews a day to ~2. `critique` is deterministic; `refine` runs only when it found something. |
| **Evaluation** | `ai/evaluator.py` | Queued to the worker; the client polls. Falls back to a heuristic scorer. |
| **Retrieval** | `ai/retrieval.py`, `ai/rag.py`, `ai/vector_store.py` | Hybrid dense + keyword with rank fusion, a distance cutoff, and an embedding cache. Benchmarked by `tests/api/test_retrieval_eval.py`. |
| **Chunking** | `ai/rag.py` | Splits on the resume's own section headings, then packs paragraphs. Chunks are rows, so re-indexing does not mean re-embedding. |
| **Redaction** | `ai/masking.py` | At the two network boundaries, so a call site cannot forget. See §7. |
| **Prompt-injection defence** | `ai/untrusted.py` | Resume text and answers are fenced with a per-prompt random nonce. Structural, not phrase matching. |
| **Object storage** | `services/storage/` | `local` or `s3`. The `s3` backend covers AWS S3, Cloudflare R2, MinIO and Backblaze B2 — same API, different `S3_ENDPOINT_URL`. Tested against MinIO, which needs no account. |
| **Chat provider** | `ai/providers.py` | `AI_PROVIDER` = gemini / anthropic / openai. The last also covers Groq, Ollama, OpenRouter and vLLM via `AI_BASE_URL`. Anthropic has no JSON mode, so replies are unfenced and extracted rather than assumed. Embeddings stay on Gemini — see `config.py` for why. |
| **Observability** | `ai/degradation.py`, `ai/call_metrics.py`, `ai/retrieval_metrics.py`, `ai/tracing.py` | Fallback rate, provider latency and token spend, retrieval outcomes; optional LangSmith tracing and Sentry reporting, both off by default and both scrubbed. |

**LangChain is used for the provider transport and the vector store only** —
`langchain-google-genai` and `langchain-chroma`. `EnsembleRetriever` and
LangGraph were evaluated and declined: the first pulls in langgraph and three of
its packages to replace forty tested lines of rank fusion, and the second has no
graph to express in a chain with one always-taken call and one conditional one.
The reasoning, and the conditions that would reopen either, are in `goals.md`.

## 7. Security Notes

- Passwords: bcrypt. Tokens: short-lived access + 7-day refresh JWTs.
- **Refresh tokens rotate and are revocable.** Every issued token is recorded by
  `jti`; refreshing revokes the old one. Presenting an already-rotated token is
  treated as replay and revokes every session for that account. Logout, password
  change, password reset and account deletion all end sessions server-side.
- **Password reset does not reveal who has an account.** `/auth/forgot-password`
  answers identically for known and unknown addresses, and delivery failures are
  swallowed rather than surfaced, because an error that only appears for real
  accounts is the same oracle by another route.
- **Email verification gates nothing** by design — the default email backend
  writes to a log, so gating would make a fresh local or demo deployment
  unusable. It is recorded and surfaced, not enforced.
- **`EMAIL_BACKEND=log` is refused in production.** It prints reset links in
  full. A production start fails until SMTP is configured; that is deliberate.
- **Direct identifiers are redacted before any text reaches the AI provider.**
  Prompts and embedding requests both pass through `app/services/ai/masking.py`,
  which strips email addresses, phone numbers, URLs, government identity
  numbers, and the account holder's own name. Employers, titles, schools,
  technologies and dates survive — they are the interview, and none of them is
  a direct identifier. This is pseudonymisation, not anonymity.
  - Redaction happens **at the two HTTP boundaries** (`GeminiClient` and
    `EmbeddingService`), not in the code that builds prompts, so a new call
    site cannot forget it. Both default to a pattern-only redactor, meaning a
    caller that omits the account holder's identity degrades to "no name
    matching" rather than to "no redaction".
  - It is **one-way**: nothing is restored on the way back, so no later bug can
    re-attach a redacted value to model output.
  - Postgres and the Chroma index still hold the resume in full. The control is
    about what crosses the network to a third party, not about storage at rest.
- **Untrusted text is fenced before it reaches a model.** The resume and the
  answers are written by the person the output is about, and the evaluator is
  the target that matters — a candidate grading themselves. Each untrusted span
  is wrapped in a fence carrying a nonce generated per prompt, so an attacker
  cannot close a fence they cannot predict. This is deliberately *not* phrase
  matching: blocklists on natural language lose to a paraphrase. It is also not
  a guarantee — what bounds the damage is that scores are clamped on parse, the
  JSON shape is validated, and evaluation output is never executed.
- Resume uploads: content-type allowlist, 5 MiB cap, opaque storage keys,
  path-traversal protection, and a per-account quota on how many are kept.
- **Rate limits and quotas are different mechanisms on purpose.** A rate limit
  is a window counter and clears by waiting; a quota is a ceiling on what is
  held and clears by deleting. Resumes held are counted from rows, so deleting
  one frees the quota and a Redis restart cannot grant unlimited uploads.
  Interviews started are a counter, because a provider call cannot be un-spent
  and counting rows would make delete-and-retry a way round the cap.
- **Security headers and CSP.** The API sends `default-src 'none'` — it serves
  JSON, so the policy's job is to make inert an error page it did not shape. The
  frontend gets a real per-request nonce CSP with no `'unsafe-inline'` for
  scripts, which costs static prerendering and is worth it while tokens are
  readable by JavaScript. HSTS is production-only.
- Account deletion is a hard delete, and clears the resume blobs and the vector
  index as well as the database rows — the database cascade cannot reach either.
- Expired refresh and one-time tokens are pruned hourly by a worker cron. Only
  *expired* rows: a revoked-but-unexpired refresh token is what makes logout
  work, and a consumed one-time token is what makes a replayed reset link fail.
- Dependencies are audited in CI (`pip-audit`, `npm audit`) with Dependabot
  raising the updates. One advisory is ignored, with a reachability argument and
  the condition that ends it.
- **The browser holds no session token.** Every API call goes through this app's
  own `/api/bff/*` proxy, which keeps the access and refresh tokens in httpOnly
  cookies and attaches the Bearer header server-side. An injected script can no
  longer read the session. Token refresh happens in the proxy, and keeps the
  distinction it has always had: an unreachable API is reported as a transport
  failure with the session intact, never as a logout.
- **Hardening backlog:** an account-wide AI budget, since per-user quotas cannot
  bound a provider quota shared by the whole deployment.
